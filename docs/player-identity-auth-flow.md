# 用户身份、Steam 绑定与选手认领梳理

## 目标

把下面几个概念彻底拆开，避免继续混用：

- 注册用户
- 未认领选手
- 已认领选手
- 已认证选手
- 注册用户并绑定 SteamID
- 管理员审核通过的选手身份

当前项目里，前端主要依赖本地 localStorage 记录一个“当前认领身份”，这只能算临时前端状态，不能作为真实的账号认证和选手认证依据。

目标是把身份体系收敛为：

1. 账号身份
2. Steam 身份
3. 选手认领申请
4. 管理员审核结果
5. 已认证选手能力

## 一、核心概念定义

### 1. 游客

未注册、未登录用户。

能力：

- 浏览公开页面
- 查看比赛、战队、选手、内容、社区

限制：

- 不能提交认领申请
- 不能绑定 SteamID
- 不能进入个人中心

### 2. 注册用户

已经拥有站内账号，但还没有完成 Steam 身份绑定。

能力：

- 登录站点
- 拥有个人账号中心
- 可以维护基础资料

限制：

- 不能提交选手认领申请
- 不能使用选手认证后的功能

说明：

注册用户不是“什么都看不到”，而是看不到需要真实身份校验的功能。

### 3. 注册用户并绑定 SteamID

站内账号已经绑定了一个 SteamID，说明平台已经拿到了第一层外部身份凭据。

能力：

- 提交选手认领申请
- 查看申请进度
- 修改或重新绑定 SteamID

限制：

- 仍然不是已认证选手
- 不能直接获得“我的选手主页”“我的战绩”“我的战队管理”等权限

### 4. 未认领选手

站内公开的 Player 档案，但尚未和任何审核通过的 User 建立正式归属关系。

说明：

- 这是内容实体，不是登录状态
- 未认领选手仍然可以公开展示

### 5. 已认领选手

建议不再单独作为模糊概念使用，统一等同于“已认证选手”。

也就是说：

- 只有管理员审核通过后，某个 Player 才算被正式认领
- “已认领选手”本质上就是“已认证选手”

### 6. 已认证选手

某个注册用户通过管理员审核，正式绑定到一个 Player。

能力：

- 拥有选手视角的个人主页
- 可维护选手相关资料
- 可查看或管理只对已认证选手开放的数据
- 可继续使用与自己身份绑定的 Steam 数据

## 二、正确的状态流转

推荐采用下面的顺序：

1. 游客注册账号
2. 成为注册用户
3. 注册用户绑定 SteamID
4. 提交选手认领申请
5. 管理员审核
6. 审核通过后成为已认证选手

审核拒绝后：

- 用户回到“注册用户并绑定 SteamID”状态
- 可以补材料后重新申请
- 也可以申请认领其他选手

## 三、模块边界

### 1. 账号模块

职责：

- 注册
- 登录
- 退出登录
- 会话管理
- 基础账号资料维护

回答的问题：

- 这个人是谁
- 他是否已登录

### 2. Steam 绑定模块

职责：

- 注册用户绑定 SteamID
- 校验 SteamID 是否有效
- 拉取 OpenDota 基础信息
- 保存 Steam 侧数据同步记录

回答的问题：

- 这个账号对应哪个 Steam 身份

不应该负责：

- 直接认领选手
- 直接授予选手权限

### 3. 选手认领申请模块

职责：

- 已绑定 SteamID 的注册用户选择某个 Player 提交申请
- 填写补充说明
- 记录申请状态

回答的问题：

- 这个账号希望认领哪个选手
- 当前申请是否待审核、通过或拒绝

### 4. 后台审核模块

职责：

- 查看待审核申请
- 通过申请
- 拒绝申请
- 记录审核备注

回答的问题：

- 这个用户是否应被认证为该选手

### 5. 已认证选手模块

职责：

- 提供已认证选手专属页面与能力
- 展示个人主页、战绩、战队、互评等

回答的问题：

- 这个登录用户是否已经具备选手身份

## 四、页面与权限建议

### 游客可访问

- 首页
- 选手页
- 战队页
- 比赛页
- 内容页
- 社区页

### 注册用户可访问

- 账号中心
- 基础个人设置
- 绑定 SteamID 页面

### 已绑定 SteamID 的注册用户可访问

- 提交认领申请页面

### 已认证选手可访问

- 我的主页

- 我的互评管理
- 其他只对认证选手开放的能力

## 五、现状问题

### 1. localStorage 被当成真实身份来源

当前 [lib/local-binding.ts](../lib/local-binding.ts) 只是浏览器本地缓存，但在交互上被当成“我已经认领了”的依据。

问题：

- 无法证明用户真实身份
- 换浏览器就失效
- 容易产生脏数据
- 会把用户带到失效的 playerId

### 2. 认领接口提交即生效

当前 [app/api/bindings/route.ts](../app/api/bindings/route.ts) 中，提交后直接把 binding 写成 ACTIVE。

问题：

- 没有管理员审核
- 没有申请阶段
- “绑定 SteamID”和“认领选手”被做成同一件事

### 3. 已认领状态并不等于已认证选手

现在顶部状态和页面入口显示“已认领”，但这个状态实际上只是“本地缓存里有一个 binding”。

问题：

- 业务含义不准确
- 容易误导用户

## 六、建议的数据模型

### 现有模型可保留

#### User

代表注册用户。

当前已有：

- id
- name
- email
- role
- playerId

建议定位：

- `playerId` 只表示审核通过后的正式选手归属

#### Player

代表站内公开选手实体。

建议定位：

- 始终是内容实体
- 不等于站内账号

#### PlayerBinding

当前更像 Steam 绑定与 OpenDota 拉数记录。

建议定位：

- 用于保存 SteamID、OpenDotaId、同步状态
- 不建议再承担“认领申请审核”的主业务语义

### 建议新增模型：ClaimRequest

建议新增一张独立申请表，用来承载审核流程。

字段建议：

- id
- userId
- playerId
- steamId
- status
- submittedAt
- reviewedAt
- reviewedByUserId
- reviewNote
- createdAt
- updatedAt

状态建议：

- PENDING
- APPROVED
- REJECTED
- CANCELLED

这样职责最清晰：

- User 负责账号身份
- PlayerBinding 负责 Steam 绑定与拉数记录
- ClaimRequest 负责选手认领审核流程

## 七、推荐关系设计

### User 与 Player

一个 User 最多绑定一个正式 Player。

适合表达：

- 这个站内账号当前已被认证成哪个选手

### User 与 PlayerBinding

建议补上用户维度关联，避免 Steam 绑定只挂在 Player 上。

因为在审核前，用户已经可能完成 Steam 绑定，但这时他还未正式归属到某个 Player。

### User 与 ClaimRequest

一个 User 可以拥有多条申请记录，但同一时间只允许一条 PENDING。

### Player 与 ClaimRequest

一个 Player 可以被多个用户申请认领，但只能最终批准一个有效归属。

## 八、前端交互应该怎么改

### 当前“认领”按钮的真实含义应拆开

建议拆成两步：

1. 绑定 SteamID
2. 提交选手认证申请

不要再用一个“认领”按钮同时完成：

- 绑定 Steam
- 自动写入玩家归属
- 自动获得选手权限

### 顶部状态建议

未登录时：

- 登录
- 注册

已登录未绑定 SteamID：

- 绑定 SteamID

已绑定 SteamID 未申请：

- 提交选手认证申请

申请待审核：

- 审核中

已认证选手：

- 我的主页
- 我的选手身份

### 我的页建议

“我的页”不应该由 localStorage 决定。

应该由：

- 当前登录用户
- 当前登录用户是否绑定 SteamID
- 当前登录用户是否拥有已审核通过的 Player 归属

共同决定。

## 九、后台需要补的功能点

### 1. 审核列表页

建议新增后台模块：

- 认领申请列表

字段建议展示：

- 申请用户
- 目标选手
- SteamID
- OpenDota 昵称
- 提交时间
- 申请状态

### 2. 审核详情页

建议支持：

- 查看该 SteamID 的基础资料
- 查看目标 Player 当前资料
- 审核备注
- 通过
- 拒绝

### 3. 审核通过后的动作

通过后应执行：

- 把 User.playerId 指向对应 Player
- 把 ClaimRequest 标记为 APPROVED
- 把相关 PlayerBinding 标记为 ACTIVE
- 清理该用户其他待审申请

### 4. 审核拒绝后的动作

拒绝后应执行：

- ClaimRequest 标记为 REJECTED
- 保留用户账号
- 保留 Steam 绑定
- 不赋予选手权限

## 十一、建议的实施顺序

### 第一阶段：补账号体系

先建立真正的注册、登录、会话。

原因：

- 没有账号主体，后面所有审核都没有承载对象。

### 第二阶段：把 Steam 绑定从认领里拆出来

先让用户成为“注册用户并绑定 SteamID”。

原因：

- Steam 绑定是申请前置，不应直接等于认领成功。

### 第三阶段：新增认领申请与审核模块

建立 ClaimRequest 和后台审核能力。

### 第四阶段：把“我的页”和顶部状态改成基于真实用户状态

逐步移除 localStorage 对身份的决定作用。

## 十二、最终建议

这块逻辑的主线应统一为：

- 注册用户是账号主体
- SteamID 是外部身份凭据
- 认领申请是待审核动作
- 已认证选手是审核通过结果

不要再让“绑定 SteamID”“认领成功”“成为选手”在同一步完成。

只有这样，下面这些概念才不会再冲突：

- 注册用户
- 未认领选手
- 已认证选手
- 待审核申请
- Steam 已绑定但尚未认证的普通用户
